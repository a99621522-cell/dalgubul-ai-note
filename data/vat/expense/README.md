# data/vat/expense — 대구 공개 지출 자료 집계(지자체 부가세 절감 점검기 '공개 지출 자료로 후보 찾기')

`scripts/fetch_daegu_expense.py`(워크플로 `daegu_expense.yml`)가 대구광역시 주민참여 재정 포털 「세출현황 — 지출건별」의 하루치 엑셀을 날짜마다 받아
(과세기간 `p` YYYY-1|2 × 회계구분 `acct` × 부서 `dept` × 세부사업 `biz` × 통계목 `mok`)로 묶은 것만 둔다: `n` 건수 · `amt` 지출액 합(원) · `card` 적요에 '카드'가 든 건수 ·
`petty` 경비구분 일상경비 건수 · `max` 가장 큰 한 건 · `memo` 적요 본보기 3개(사람 이름 묶음은 `(이름)`). 원본 행·거래처·사업자번호·세액은 없다(포털에도 없음).

- 포털 회계연도 목록은 2015~2024 이지만 건별 자료는 2023년까지(2026-11-03 확인, 2024년 뒤는 빈 응답) — 경정청구 기한 안 과세기간 가운데 2021년 2기~2023년 2기
- 세액은 화면이 통계목 성격(`src/lib/vatExpense.ts` `MOK_CLASS`)에 따라 지출액 × 10/110 을 **추정**으로 보인다. 실제 공제는 세금계산서 원본으로 확인한다. 평가 없음
- `index.json`: 지자체별 이름·받은 날·과세기간·묶음 수
- 러너 VM 의 IP 에 따라 포털이 TCP 연결을 막는다(2026-11-03 중구: 3.6시간 동안 연결 0건, `revenue_docs.yml` 과 같은 현상). 수집기는 연도 목록을 못 받거나 12일 연속 실패하면 중간 저장 뒤 **종료 코드 3** 으로 끝내고, 막힌 잡이 자기 지자체만 같은 워크플로로 새 러너(새 IP)에서 다시 부른다(입력 `attempt`, 50번째까지 — 러너 약 30대 중 1대꼴로만 연결됨; 지자체마다 따로라 한 곳이 오래 받아도 나머지가 기다리지 않고, 같은 지자체 실행은 concurrency 로 하나씩). 데이터를 커밋한 잡은 `deploy_vat.yml` 을 불러 점검기에 바로 싣는다(봇 커밋은 push 배포를 깨우지 않음). 받은 날은 JSON 에 남아 다음 실행이 이어 받는다
- **2026-11-03 23:20 UTC 쯤부터 포털이 GitHub 러너 요청을 400 쪽(1,414B)으로 막는다.** 남구가 그때까지 218일을 받다가 12일 연속 실패로 멈췄고, 그 뒤 연결된 러너는 연도 목록을 그대로·화면 쿠키·쿠키+XHR 머리글 세 가지로 해도 모두 같은 400 쪽(동구·군위군·달서구·남구·서구·달성군에서 확인). 요청 형식이 아니라 막힘이라 그날 체인을 모두 멈췄다(남은 곳: 동구·서구·남구 나머지·북구·수성구·달서구·달성군·군위군). 다시 할 때는 `probe=true` 한 번으로 연도 목록이 JSON 으로 오는지부터 보고, 되면 지자체를 하나씩 차례로(동시에 여럿 돌리지 않는다). 계속 막히면 국내 PC 에서 `python3 scripts/fetch_daegu_expense.py --gov <key>` (이어 받기)
