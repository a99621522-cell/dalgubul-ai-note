# 프롬프트 — '지난 돈 돌려받기'를 처음 쓰는 공무원이 가장 편하게 (UI/UX 전문가 판)

> 쓰는 법: 이 파일 전체를 Claude Code 세션에 붙여 넣고 "그대로 실행해"라고 한다.
> 만든 날 2026-11-05. 대상 화면 https://vat-daitda.pages.dev/vat/review/ (저장소 `src/pages/vat/review/index.astro`).

---

## 0. 너의 역할

너는 공공 서비스 UX 리서처이자 인터랙션 디자이너다(정부24·홈택스 같은 민원 서비스 개선 경험 15년, 쉬운 공공언어·WCAG 2.2 AA 전문).
목표는 하나다 — **세무·회계 전문가가 아닌 지자체 부가세 담당 공무원이, 처음 열어 보고도 10분 안에 "우리 기관이 얼마를, 왜, 어떻게 돌려받는지"를 알고 경정청구 자료를 내려받게 한다.**
화면을 예쁘게 하는 것보다 **생각할 일·고를 일·읽을 글을 줄이는 것**이 먼저다.

## 1. 쓰는 사람 (페르소나 2)

| | 가 — 처음 맡은 주무관 | 나 — 결재하는 팀장 |
|---|---|---|
| 상황 | 부가세 업무 6개월 차, 세법 용어 낯섦, 홈택스에서 신고서 PDF 는 받을 줄 앎 | 숫자와 근거 한 장만 보고 결재 |
| 원하는 것 | "무엇을 올리면 되나", "얼마 나오나", "다음에 뭘 하나" | "얼마 · 왜 · 근거 조문 · 위험(가산세)" 한 쪽 |
| 불안 | 틀린 숫자로 경정청구했다가 문제 될까 | 근거 없는 금액에 결재 |
| 기기 | 사무실 PC(1366×768, 크롬·엣지), 가끔 휴대폰으로 확인 | PC·출력물 |

## 2. 바꾸면 안 되는 것 (제약)

- **규칙·계산은 한 줄도 바꾸지 않는다** — `vat_rules.ts judge`, `vat_diag.ts`, `vat_unlock.ts`, `rules.yml`. 화면·문구·순서·보여 주는 방식만 바꾼다. 계산 값이 바뀌면 실패다.
- 서버·AI 호출 없음, 파일은 브라우저 안에서만 읽는다(이 문장은 화면에 남긴다).
- 모든 결과 화면에 '판정은 참고이며 기관의 판단이 아닙니다'. 평가·'절세' 문구 금지, 담당자 이름·전화 없음.
- 다잇다 사이트와 서로 링크하지 않는다. 배포는 `/vat/review/` 한 화면(`deploy_vat.yml`).
- 기존 수용 시험 `scripts/vat_ux_test.mjs` 는 모두 통과해야 한다(선택자가 바뀌면 시험을 같은 뜻으로 고친다 — 값 비교는 그대로).

## 3. 지금 화면에서 이미 보이는 문제 (출발점 — 검증하고 더 찾아라)

1. 첫 화면에 **'0 원' 금액 띠**와 **'파일을 모두 여기에 놓으세요' 칸**이 ① 기관 고르기보다 먼저 나온다 — 순서가 뒤집혀 무엇부터 할지 헷갈림.
2. 파일 단추가 브라우저 기본 영어 **'Choose Files / No file chosen'**.
3. 머리 안내문이 세 줄 넘고, 글자 크기 단추·문맥 바·제목 띠가 본문보다 먼저 시선을 뺏는다.
4. 결과에 **(16)(17)(18), 안분, 면세비율, 정산, 재계산, 과세표준 명세** 같은 서식 용어가 그대로 — 설명은 `?` 안에 숨어 있음.
5. '지난 신고 진단', '할 일', '돌려받을 돈 표', '고친 신고서', '자세히 보기'(금액 카드·자료별·②·④·근거·사유), 가산세 계산기, 사례·감사 묶음이 한 화면에 이어져 **결과가 어디서 끝나는지** 모름.
6. 내려받기 단추가 여러 군데(엑셀만·PDF 만·zip·묶음·Word) — 무엇을 받아 누구에게 주는지 모름.
7. 확인 질문·계약 어림(회색)·확정/최대/어림 세 금액이 섞여 **'그래서 얼마?'** 가 한 숫자로 안 보임.
8. 휴대폰에서 표가 카드로 바뀌지만 여전히 길다.

## 4. 하는 순서

### 4-1. 측정 먼저 (before)
Playwright 로 고정 자료 `scripts/fixtures/hometax/dalseong5y/`(10개 과세기간, 심은 오류 8가지, 확정 460,000원·최대 5,200,000원)를 써서 **과업 4개**를 재고 `docs/design/vat-review-ux-before.tsv` 로 남긴다.

| 과업 | 끝나는 조건 |
|---|---|
| A. 기관 고르고 신고서 10개 올려 첫 금액 보기 | 돌려받을 돈(확정) 숫자가 보임 |
| B. "왜 그 금액인가"를 한 과세기간에 대해 설명하기 | 그 기간의 이유·근거 조문이 화면에 보임 |
| C. 경정청구에 쓸 파일 받기 | 엑셀(또는 zip) 내려받기 완료 |
| D. 팀장 결재용 한 쪽 받기 | 검토 보고(Word/PDF) 내려받기 완료 |

재는 것: 클릭·입력 수, 스크롤 화면 수(1366×768·390×844), 첫 금액까지 화면에 보이는 글자 수, 처음 보는 용어 수(괄호 칸 번호·세법 용어), 결정 지점 수(고르거나 판단해야 하는 곳), axe 위반 수.
그리고 페르소나 '가'로 **인지적 워크스루**(단계마다: 무엇을 하려 하나 / 할 것이 보이나 / 보인 것과 하려는 것이 이어지나 / 한 뒤 맞게 됐다고 아나)와 닐슨 휴리스틱 10개 점검표를 `docs/design/vat-review-ux-audit.md` 에 쓴다. 문제마다 심각도 0~4.

### 4-2. 설계 원칙
1. **한 화면 한 할 일** — 지금 할 일 하나만 강조 단추, 나머지는 회색·접힘.
2. **순서 = 일의 순서** — ① 기관 → ② 파일 → ③ 결과. 아직 못 하는 단계는 잠그고 이유를 한 줄로("기관을 고르면 열립니다").
3. **결과는 역피라미드** — 맨 위 한 문장: "**○○군은 경정청구로 약 N원을 돌려받을 수 있습니다(확정 N원 + 확인하면 최대 M원).**" → 그 아래 과세기간별 한 줄씩(기간 · 무엇이 틀렸나 · 얼마 · 기한) → 펼치면 근거 조문·고친 신고서 칸.
4. **쉬운 말 먼저, 서식 칸은 괄호로** — "공제받은 매입세액 (18)"처럼 뜻 → 칸 번호 순. 용어 사전은 처음 나올 때 한 번 풀어 쓴다.
5. **금액은 세 종류를 섞지 않는다** — 확정(굵게) / 확인하면 늘어날 수 있는 몫(보통) / 참고 어림(회색, 기본 접힘).
6. **내려받기는 받는 사람 기준 두 개** — 「세무서·홈택스에 낼 자료(엑셀+PDF 묶음)」, 「결재용 한 쪽(Word)」. 그 밖의 형식은 '다른 형식' 접힘.
7. **질문은 결과 뒤에 꼭 필요한 것만** — 금액을 크게 바꾸는 질문 3개까지, "답하면 +N원 달라질 수 있습니다"를 함께.
8. **오류·빈 상태·읽는 중**을 모두 설계 — 읽지 못한 파일은 파일 이름 + 이유 + 어떻게(예: "스캔한 PDF 는 글자가 없어 못 읽습니다 — 홈택스에서 다시 출력").
9. **한국어 파일 단추** — 기본 input 을 숨기고 「파일 고르기」 단추 + 끌어다 놓기 칸, 놓은 파일 목록에 종류(신고서·명세서·매입 목록)·과세기간 배지.
10. **신뢰 신호** — 금액 옆에 "신고서 몇 장·매입 몇 건으로 계산" 출처 사슬, 계산은 참고라는 문장, 근거 조문 링크.
11. 접근성: WCAG 2.2 AA, 키보드만으로 과업 A~D, 초점 순서 = 화면 순서, 색만으로 뜻 전달 금지, 휴대폰 390px 가로 스크롤 없음, 인쇄 A4 에서 결과 한 쪽 요약.

### 4-3. 설계 문서
`docs/design/vat-review-ux-spec.md`: 화면 구조(첫 화면 / 파일 올린 뒤 / 결과 / 내려받기)의 와이어프레임(글자 그림), 컴포넌트 목록(단계 표시·파일 칸·결과 요약 문장·기간 행·근거 펼침·내려받기 두 단추), 문구표(지금 문구 → 바꿀 문구, 용어마다), 상태표(빈·읽는 중·부분 성공·실패·결과 0원), 수용 기준(아래 5).

### 4-4. 구현
작은 커밋 5개 이하로, 커밋마다 빌드(`VAT_SITE=1 npx astro build`)·수용 시험(`node scripts/vat_ux_test.mjs --no-axe`) 통과 뒤 다음으로.
결과 0원일 때("찾은 것이 없습니다 — 이런 경우일 수 있습니다: …")와 신고서를 일부만 올렸을 때("2022년 제1기 확정이 없습니다 — 올리면 더 찾을 수 있음")를 반드시 넣는다.

### 4-5. 측정 (after) · 보고
같은 과업 4개로 `docs/design/vat-review-ux-after.tsv`, before 와 나란히 표. 시험에 과업 A~D 를 시나리오로 더한다(키보드만 변형 포함). 1366·390 스크린숏(첫 화면·결과)을 운영자에게 보낸다. CLAUDE.md 에 한 단락. main 과 지정 브랜치에 푸시하고 배포 확인.

## 5. 수용 기준 (모두 맞아야 끝)

| 기준 | 목표 |
|---|---|
| 과업 A 클릭·입력 수 | 4 이하(기관 고르기 1 + 파일 고르기 1 + 놓기/열기) |
| 과업 A 스크롤 | 1366×768 에서 0화면 — 첫 금액이 파일을 놓은 자리 바로 아래 보임 |
| 첫 화면(파일 전) 글자 수 | 지금의 절반 이하 |
| 결과 첫 화면의 낯선 용어 | 풀어 쓰지 않은 서식 칸·세법 용어 0개 |
| 결과 요약 | 한 문장 + 기간별 행, 금액 종류 섞이지 않음 |
| 내려받기 | 강조 단추 2개(제출 자료·결재용), 나머지 접힘 |
| 계산 값 | 고정 자료 확정 460,000원·최대 5,200,000원 그대로, 기존 시험 전부 통과 |
| 접근성 | axe 위반 0(1366·390), 키보드만으로 A~D 완료 |
| 휴대폰 390px | 가로 스크롤 없음, 결과 요약이 첫 화면 안 |

## 6. 하지 말 것

- 새 기능(새 계산·새 자료 수집) 추가 금지 — 이번 일은 '쉽게'뿐.
- 화면을 늘리는 쪽(새 안내 상자·새 경고)보다 **빼고 접는 쪽**을 먼저 고른다. 무엇을 뺐고 어디로 옮겼는지 표로 남긴다.
- 홈택스·국세청 화면을 흉내 내지 않는다(로고·색).
- 운영자에게 확인 질문을 하지 말고, 판단이 갈리면 위 원칙 순서대로 정하고 문서에 이유를 적는다.
